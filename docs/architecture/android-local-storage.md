# Android local storage

Roadmap PR-04. Implementation is under `modules/lody-kit/android/.../storage`, registered through `LodyKitModule`, and exported through the Android typed facade. Product auth/catalog routes remain gated by PR-09. Emulator acceptance is pending until the storage case report exists.

## Credentials

`AuthCredentials` uses an AES-256-GCM key generated by the AndroidKeyStore provider. A provider-generated 12-byte IV accompanies a versioned encrypted envelope; the key alias is authenticated as additional data. Tokens are bounded at 64 KiB, temporary plaintext byte arrays are cleared, and the envelope is atomically replaced in `Context.noBackupFilesDir`. Long-lived credentials do not enter a WebView or the SQLite projection cache.

A missing key, failed authentication tag or malformed envelope deletes the unusable credential and returns `credential_reauthorization_required`. The next authorized save creates a fresh key. Storage I/O failures remain errors; they do not report a successful save. Logout removes the file and key. Android backup is explicitly disabled in app config, and the credential/projection files independently use the no-backup directory.

All Keystore and database operations use the module's serial storage worker. The implementation follows the [Android Keystore provider contract](https://developer.android.com/privacy-and-security/keystore); emulator results do not establish hardware-backed key storage or StrongBox availability.

## Display projections

`LocalStore` maintains schema version 1 with a bounded key/value cache. Keys and serialized values keep the existing shared `readLocalValue` / `writeLocalValue` contract; keys are bounded to 1 KiB and values to 12 MiB UTF-8. SQL arguments are bound. Embedded NUL values are rejected rather than silently truncated by SQLite text functions.

Large values are reconstructed through 65,536-character SQLite substrings so a complete catalog does not need to fit inside one CursorWindow row. A single storage owner serializes reads and writes; startup restores the account, validates the selected workspace against that account's workspace list, and reads only its corresponding catalog key. Saved projections carry their prior sync timestamp and are not evidence of a live connection. Credentials and CRDT state do not belong in this table.

Clear invalidates the native storage generation before queued work, closes the currently owned internal runtime probes, and deletes cached values on the worker. Native delayed writers carry the generation captured before queuing; a replaced context rejects that write. A malformed account fails startup explicitly. Explicit cache clearing can recover a corrupted database. Full logout/account-switch UI integration and session runtime persistence are completed when PR-09 opens those capabilities; the shared JS generation/abort contracts remain necessary for callbacks that have not yet reached native code.

## Offline verification

`runStorageVerification` invokes the actual production storage classes with isolated fixture filenames and aliases. The first invocation generates a synthetic credential and saves a projection over 2 MiB. The Android runner force-stops the app and relaunches it; the second invocation requires a different PID, verifies the encrypted credential and full Unicode projection, switches account/workspace, deletes the actual Keystore key, saves with a new key, and rejects an old-generation write after clear.

Only non-secret case metadata, process IDs, projection size and restore duration are written to the external evidence report. A synthetic credential hash stays in the private fixture database only until the case clears it. Fixtures never use desktop credentials or a real Cloud account. The large projection is a storage stress fixture, not proof that a product screen has rendered that catalog.
