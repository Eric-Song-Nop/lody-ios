# Android 逐 PR 交付清单

日期：2026-09-10。配套[阶段路线图](2026-09-10-android-pr-roadmap.md)和[平台能力契约](../architecture/android-platform-contracts.md)。本文细化执行边界，不改变已有 PR 的完成状态，也不表示候选依赖已在产品中可用。状态、真实 PR 链接和验证报告统一登记在路线图。

## 使用方式

阅读顺序：先看[阶段交付总览](#阶段交付总览)，再用[堆叠与准入表](#实际子-pr-的堆叠与准入表)确定父 PR，最后按对应阶段、代码落点及评审演示执行。README 的精细优化另见[组件工作包](#readme-组件的子-pr-工作包)，选型 PR 按[具体交付物](#选型-pr-的具体交付物)收尾；两者补充验收范围，不新增 PR 或另立完成状态。

按当前要做的工作直接定位：

| 工作                    | 执行入口                                                                                             | 审查时要得到的结论                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 创建下一个 PR           | [父 PR 与能力准入](#实际子-pr-的堆叠与准入表)、[代码落点](#逐-pr-代码落点与交接文件)                 | 本次 diff、前置能力与交接对象明确               |
| 落实 WASM 必需能力      | [02～04 实施顺序](#pr-0204先证明真实-wasm再建立恢复与持久化)、[完整兼容包](#pr-0204完整-wasm-兼容包) | 真实资产通过；可选 Sandbox 对照不替代基线       |
| 替代 Swift 聊天渲染组合 | [README 组件工作包](#readme-组件的子-pr-工作包)、[06 前固定输入](#pr-06-前冻结的测试输入清单)        | 公式、高亮、渐入、选择、回收和滚动分别有证据    |
| 决定是否采用 Enriched   | [06～07b 实施顺序](#pr-0607b把支持流式拆成可验收的聊天行为)、[选型交付物](#选型-pr-的具体交付物)     | 06 提供原型差异，07a 验证流式正确性，07b 才定案 |
| 结束一个阶段            | [集成验收流程](#阶段集成验收的执行脚本设计)、[阶段报告模板](#阶段验收记录模板)                       | 最终同一版本的模拟器结果与未执行项清楚分开      |
| 提交评审                | [收尾清单](#每个-pr-的收尾清单)、[PR 正文模板](#可直接使用的-pr-正文模板)                            | 审查者能够复现行为并确认后继入口是否可开放      |

每行是一个实际 PR 的审查单元。已有 PR-00～05b 保持原有边界；后续默认按照表中子编号依次堆叠。后继 PR 的 Git base 是紧邻父分支，能力准入另外按路线图检查。跨阶段提前制作离线 fixture 可以独立进行，产品接线必须等待前置验收。

每个 PR 从现有 kit facade 出发，在正文列出本次涉及的导出、调用方、真实实现和未开放入口。第一方 Kotlin 实现通过同一个 `LodyKitModule` 注册。不能为了让入口编译成功而补空实现。

审查材料随实现提交；证据随实际验证更新。下面的 case ID 沿用路线图，是验收要求，不保证已有同名 runner 命令。可执行参数以 [Android runner 文档](../../apps/mobile/verification/android/README.md)为准。

## 关键能力包的具体实施顺序

以下步骤细化现有审查单元，不增加必需 PR 数量，也不修改完成状态。实现时按各 PR 的开始条件推进；已经有实现的部分先核对证据与契约，只补缺口。

### PR-02～04：先证明真实 WASM，再建立恢复与持久化

1. **02 · 固定资产**：从现有资产生成链路产出 JS、Loro/Flock WASM 和依赖许可证，记录哈希。列出实际用到的浏览器 API、加载路径与桥接消息；离线 fixture 与真实运行时使用同一资产。
2. **02 · 跑通完整数据路径**：Kotlin 创建本地 WebView，等待真实初始化结果，依次执行 bootstrap、增量输入和完整投影输出。随后覆盖拆开的 uint32 大端长度头、payload、压缩输入及桥接分块；逐字段比较投影，不能只检查“加载成功”。
3. **02 · 封住输入与队列边界**：定义单副本 8 MiB 上限、损坏输入和背压结果。保存失败样例与实际错误；尚未完成的投影不得进入 live 状态。
4. **03 · 补生命周期**：在原生侧实现启动/心跳 deadline、generation 隔离和有限重启。分别注入初始化未完成、renderer 退出、后台暂停、替换后旧回调以及主动停止；核对请求结算和订阅清理。
5. **04 · 接安全恢复**：长期凭据进入 Keystore 保护的私有存储，完整显示投影进入 SQLite。先验证离线恢复，再验证重新认证、切换账号和退出；将密钥失效、损坏与迟到写入作为独立失败用例。

阶段交接要同时提供成功投影、故障状态和停止后的资源状态。Sandbox 对照复用这些资产、输入与预期；它只影响可选宿主优化，不改变 WASM 必须交付这一要求。

### PR-05a～05b：先固定宿主，再逐批验收系统交互

05a 先交付导航生命周期；05b 沿用路线图中的五批次，不新增重复的父 PR。已有通过记录按其构建版本保留，下面列的是收尾要求，不表示重新开始已完成的实现。

1. **05a · 固定退出契约**：列出 push、sheet、系统 Back、交互返回取消和卸载的结果；验证 `present` 只结算一次、监听及时释放、`sessionNav` 不重复消费。后续控件共用这些生产宿主。
2. **05b · 控件与图标**：逐项核对 facade 对应的真实 Android 实现，覆盖启用、禁用、点击、长按和图标语义。page/sheet 与深浅色分别检查；点击区至少 48 dp，图标可见不能代替标签和动作正确。
3. **05b · 菜单与列表**：核对选择和取消次数、长按不误触子动作、列表回收及动态插入/删除的锚点。导航返回分别验收键盘焦点和 TalkBack 焦点；原行已删除或用户已移到其他控件时，不抢回焦点。
4. **05b · 主题、语言与字体**：在页面仍打开且存在本地状态时切换外观、语言和字体，核对正文、原生菜单、系统栏和草稿。资源对照检查与完整页面检查分别记录；增加字体检查不引入专门的超大字体重挂载逻辑。
5. **05b · 系统能力与提示**：核对偏好在进程重启后恢复、剪贴板内容准确、提示显示和消失，以及键盘出现时的位置。默认提示时长与无障碍设置下的行为分开检查；触觉仅凭模拟器不判定物理体验通过。
6. **05b · 合并验收矩阵**：在最终 APK 上检查受影响宿主的触屏、键盘和 TalkBack，再回归 05a 的 Back、关闭和中断返回。TalkBack 必须观察实际焦点、探索时不触发动作、激活只执行一次及退出后的设置恢复；仅启用服务不足以通过。

收尾报告按“批次 × 宿主 × 外观 × 输入方式”列出适用用例、结果及证据版本。第三方原生依赖如需补丁，必须持久化补丁与锁文件、保留原失败用例，并完成对应 Android 和正常签名 iOS 构建；旧 APK 的通过不能关闭新补丁的验收项。完整 05b 通过后才满足 PR-06 的平台 UI 前置条件。

### PR-10a～11b：先证明写入顺序，再开放发送入口

### PR-12a～13b：独立视图宿主与文件生命周期

1. **12a · 先实现独立 Diff owner**：复用 Pierre 构建资产，定义预热、租用、加载、关闭和销毁状态。每次加载携带文件身份与请求版本；用快速切文件、关闭重开和迟到回调证明不会闪现旧内容。
2. **12a · 验证与数据宿主并存**：后台持续输入固定数据增量，同时反复开关 Diff；核对投影继续前进、数据 owner 未替换、Diff 资源在释放后回落。Diff 不能拥有或销毁数据副本。
3. **12b · 接原生内嵌视图**：先渲染共享变更模型，再接工具栏和全屏跳转。覆盖空变更、长行、大变更和错误状态；从内嵌打开全屏时核对同一文件与版本，不重新推断文件身份。
4. **13a · 固定请求及缓存边界**：请求关联账号、工作区、路径和版本。测试 A 路径慢响应晚于 B 路径返回、页面关闭、账号切换和机器离线；缓存读写都必须校验当前上下文。
5. **13b · 先选型再接预览**：用同一文件集比较 Sora 只读候选与轻量方案，记录可读性、搜索定位、包体和内存。按代码、图片、PDF、未知类型明确处理方式，逐项验证 MIME、受控 URI、权限失效、大小边界与关闭清理。

预览器尚未定案不阻塞已通过的文件目录能力，但不得开放一个没有真实实现的预览入口。12a 的宿主协议变化必须复验数据同步并存；13b 的文件持有关系变化必须复验 11a 的上传与取消。

### PR-14～15b：通知消费与用户任务后台恢复

1. **14 · 先完成离线点击协议**：在 LodyKit 持有原生监听和待处理点击，RN 确认后再消费。用冷启动、授权尚未恢复、重复点击和账号切换 fixture 检查只路由一次，且目标来自当前账号 catalog。
2. **14 · 再验证真实提供方**：通过 config plugin 固化配置，用专用设备记录权限允许/拒绝、前后台和冷启动推送。明确 GMS、无 GMS 与渠道覆盖；离线通知场景保持不初始化 SDK、不请求真实权限。
3. **15a · 明确任务边界后选择机制**：先写出用户开始发送、等待回复同步、完成、失败及取消的事件表，再核验目标 Android 版本允许的后台机制、声明和通知要求。实现只持有正在执行的用户任务，不把后台服务用于空闲保活。
4. **15b · 注入系统中断**：覆盖切后台、网络切换、任务取消、进程终止和返回前台。恢复只补读与重建必要订阅；记录写命令次数，证明系统恢复没有再次发送或创建会话。

阶段 E 的模拟器验收证明组合行为；推送提供方、真实触觉及 OEM 后台限制分别需要真机证据。缺少证据的设备范围保持未验证，不能通过后台任务 API 返回成功来关闭验收。

### PR-16～17b：用最终构建完成质量与发行验收

1. **16 · 固定测量条件**：在执行前冻结设备、输入、构建类型、采样方法及预算。复用 06 的流式与长历史输入，并加入聊天、Diff 和数据同步并存；分别记录帧耗时、内存、解析次数、队列及恢复时间。
2. **16 · 按实际瓶颈修复**：每次修复保留同条件的前后结果。最终版本重跑受影响用例与阶段集成流程；不能把多个 APK 上的局部通过拼成最终包通过。
3. **17a · 固化可再生发行构建**：在干净环境生成并构建 APK/AAB，核对签名接入、ABI、16 KiB、R8、离线资产路径与许可证。Android 和 iOS 的构建结果分别记录，保留 iOS 正常签名。
4. **17b · 验证升级及更新隔离**：从选定旧版本安装升级，覆盖本地投影、凭据失效、schema 兼容和进程重启。核对平台、渠道、native runtime 与 JS/WASM 资产匹配；不兼容更新必须被拒绝或明确禁用该 OTA 路线。
5. **17b · 收尾交付**：将最终源码、资产哈希、安装包、验收报告和实际支持范围关联起来，更新 README 与内部发行说明。所有必需 PR 达标才关闭计划；创建 PR、内部包验收和公开发行分别记录。

## 控制单个 PR 的范围

默认使用上面的 28 个审查单元。若单个 PR 同时引入新宿主、替换渲染引擎并接通真实写入，必须重新划分范围；这三类变化无法用一份原型证据共同验收。新增子编号时同时修改阶段总览、直接依赖和交接表，保留既有真实 PR 的编号和链接。

- **原型 PR**交付可运行的内部场景、测量和缺口；不顺带开放产品按钮。
- **正确性 PR**在固定输入上解决状态与生命周期问题，失败用例随修复保留。
- **接线 PR**消费已验证契约，重点验收取消、错误、账号隔离和用户可观察结果。
- **发行 PR**验证最终包及升级路径；不能用构建成功代替功能与真机验收。

排期以阶段门槛推进，不预填未经原型验证的人日。PR-06 的结果决定 07 是否需要 X3；真实 WASM 兼容失败阻塞数据路线，不能以 Markdown 已能显示来绕过；Sandbox 对照即使失败，也不阻塞已达标的 WebView 宿主交付。

### PR-06 的依赖选择记录

### 单个 PR 的执行顺序

每个审查单元按以下顺序推进。它们是同一个 PR 内的工作步骤，不增加必需 PR 数量；提交数量按实际改动决定。

| 步骤              | 具体工作                                                                                | 退出条件                                                          |
| ----------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 1. 固定边界       | 核对能力前置、父分支、涉及的 facade 与宿主；为新增行为登记 fixture 输入、预期和失败结果 | 消费方能据此实现；未实现能力不会被 Android 入口导入               |
| 2. 交付最小行为   | 实现真实原生能力和内部场景，先打通一条完整成功路径，同时实现取消、错误结算和资源释放    | 可以在离线场景中观察真实结果；不以 stub 或固定成功值代替          |
| 3. 补齐边界与验证 | 执行本 PR 的故障、生命周期及受影响宿主矩阵；修复后使用新构建复验，保留原失败证据        | 必需行为、视觉与时序检查分别有结论；共享原生变化完成对应 iOS 回归 |
| 4. 接线与交接     | 仅开放本 PR 获准的入口；更新能力契约、证据索引、下一 PR 消费的样例及未完成项            | PR 描述对应最终实现；前置验收完整后，下游才消费该能力             |

原型 PR 的第 4 步交付内部入口和决策材料；产品接线仍由表中指定的后续 PR 承担。遇到新依赖兼容性失败，先缩小到可复现样例并记录决策，不把未通过部分挪出验收范围。

阶段报告由该阶段的收尾 PR 维护，路线图只链接报告并记录总状态。以下模板用于区分单项通过、组合通过和仍缺少的证据。

| 受影响的前序能力     | 按接口变更回归表选取       | 待执行 |                      |

没有适用场景的行写明原因；缺少规定证据的行保留待验证。某个主题、宿主或输入子集通过，只关闭对应项，不能直接将整阶段标记为通过。旧 APK 结果可以保留作为历史基线，但不能证明后来新增的原生资源或行为。

- 在正文列出父 PR、计划编号、本次可观察行为、实际修改范围及仍未开放的入口。
