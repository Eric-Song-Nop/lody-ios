日期：2026-09-10。状态：实施中。本文是分 PR 的交付计划；远端 PR 和验证状态见阶段表，候选方案仍须通过对应验收。

依据：[组件研究](../research/android-native-alternatives.md)、[源码与发布包证据](../research/android-native-alternatives-evidence.json)、[项目 README](../../README.md)及本轮讨论。版本观察截至研究日期；实际引入依赖时重新核验并锁定。PR 编号是本文内部编号，未来在进度表中补真实链接。

**1. 已确定的方向与待定事项**

已确定的要求：

- Android 必须运行当前 Loro/Flock WASM 数据核心及必要的配套 JS，维持与官方 Cloud 的协议兼容。
- 保留 Expo Router、React Native、pnpm workspace 和现有 LodyKit 边界；第一方 Android 原生能力集中于同一个 LodyKit，通过 `LodyKitModule` 注册。
- iOS 继续使用现有 Swift 实现。共享模型、协议、页面流程、语言源和行为样例，平台分别实现原生交互。
- Android 数据运行时先以离屏 WebView 建立兼容基线；JavaScriptSandbox 是可选优化，需要完整资产验证。
- 聊天优先验证 Enriched 的 RN Android 实现。它支持流式；独立 Kotlin SDK 尚不能按同等能力规划。
- 不在 RN 新建第二份 live CRDT replica，不自动重放发送，不将长期凭据交给运行时。
- 保留 Pierre 全屏 Diff；数据运行时 WebView 与 Diff WebView 独立管理。

待 PR 决策记录定案的项目：

**2. 交付规则与统一验证**

每个 PR 只交付一个可以独立审查的能力，描述须包括：用户可观察的结果、代码范围、输入输出契约、证据、已知限制和依赖 PR。任务复选框表示该项实现及对应检查已完成，不代表 PR 已合并；阶段表另行记录 `待开始 → 实现中 → 验证中 → 验证通过 → 已合并`，失败时记录阻塞项。draft 是评审状态，可以与上述实现状态并存。阶段完成要求所属必需 PR 的验收全部通过，合并与发行分别记录，不能相互替代。

前期 Android 入口限定为开发或内部构建的明确验证入口。不得为未实现接口注册返回空值或虚假成功的桥接 stub。当前 `NativeChat.tsx` 使用 `requireNativeView('LodyKit', 'LodyChatView')`，平台拆分要确保 Android 模块图不会提前加载未实现的 iOS 视图；只把已实现能力接入对应入口。完整产品入口在 PR-09 开始开放，发布由 PR-17 控制。

生成的 `apps/mobile/android` 与 `apps/mobile/ios` 都不作为唯一配置来源。改动持久化在模块、app config、config plugin 和资产构建脚本中；prebuild 后可以再现。任何停用、回退都通过后续提交或发行开关实现，不覆盖用户工作树，不回滚已经提交到 Cloud 的操作。

**Stacked PR 的具体推进方式**

工作依赖允许独立开展，Git 堆叠则采用一个可追溯的默认主链：`PR-00 → PR-01 → … → PR-17`。例如 PR-05 的能力依赖只有 PR-01，但按默认主链提交时仍以 PR-04 分支为 base；不要把 Git base 与能力依赖混为一谈。确需分叉时，在 PR 正文列出汇合前置条件，再显式调整后续 base。

- 已有 `android/00-platform-contracts` 和 `android/01-native-bootstrap` 分支保留；后续新分支默认使用 `codex/android-02-wasm-runtime` 等 `codex/` 前缀。
- 只向用户 fork 推送。主链中的子 PR 指向紧邻父分支，PR 正文同时链接父 PR 和本计划编号；不全部指向 `main` 制造累积 diff。
- 每个 PR 先形成可构建的独立提交，再附离线证据。原型只进入内部验证入口，产品入口开放遵循 PR-09 及后续能力门槛。
- 父分支有修正时，将修正同步到子分支，并重新验证受影响的 case；不能继续引用旧 APK 的证据来证明新代码通过。
- 父 PR 合并后再调整子 PR 的 base，检查 diff 只剩该 PR 的改动；不把建立堆叠视为自动授权合并或发布。
- 某个 PR 需要进一步拆小时使用 `PR-07a / PR-07b` 等子编号，并更新能力清单与依赖表；父编号所有必需子项通过后才能通过阶段门槛。

**阶段验收报告模板**

每阶段在 `docs/research/` 保留一份报告或更新现有证据索引。阶段报告引用逐 PR 证据，并记录阶段最终版本的集成结果，避免读者从多个失败轮次自行猜测当前状态。

```text
阶段：A / B / C / D / E / F
包含的计划编号与真实 PR 链接：
验收版本：commit、工作树状态、APK SHA-256、资产/fixture 哈希
环境：AVD、API、ABI、构建类型、WebView provider（如适用）
执行入口：实际命令、case ID、产物目录
结果：每个必需 case 的通过/失败及截图、视频或 trace
集成检查：本阶段各组件在同一版本下组合运行的结果
iOS 回归：本次影响范围、实际执行项及结果
未决项：环境失败、未执行项目、真机和真实服务联调缺口
入口决定：允许开放的能力、仍保持内部可见的能力
阶段结论：验证中 / 本机模拟器通过 / 全部规定验收通过
```

“本机模拟器通过”只确认对应本机门槛，不替代 CI、实机或发行状态。重跑保留原失败报告，新报告标明修复提交和替代的轮次；如果剩余问题影响后继契约，依赖项继续保持阻塞。

**Markdown 流式验收与选型决策**

PR-06 先固定以下样例及输入节奏，PR-07 使用同一组输入验收；PR-16 复用它们做 release 性能回归。下列规模是计划中的基线，不是已经测得的性能承诺。

- 静态语料：中英文段落、嵌套列表、任务列表、表格、代码、行内及块级公式、图片、链接和工具块；保存最终 Markdown 与约定复制文本。
- 流式语料：逐字符、按短块持续追加、一次大块突发、完成事件先于显示追赶；覆盖未闭合代码/公式、emoji 与组合字符，以及全文替换、等长修正、删除回退和后置引用定义。
- 列表语料：至少 1,000 条混合历史消息，顶部补页 100 条；分别在底部、上翻阅读、文本选择中追加消息，并让图片延迟获得尺寸。
- 测量记录：固定设备与输入时间序列，记录解析/布局次数、队列峰值、文本收敛、滚动锚点及内存趋势。动画是否导致重复全文解析须有探针或 trace，不能根据观感推断。

选型决策记录逐项写明“直接通过 / 有界扩展后通过 / 未通过”，附复现 case、修改归属、维护成本和上游跟进方式。Enriched 支持流式这一点，不自动等于字符渐入、稳定块复用、跨块选择和 FlashList 回收均已符合本项目要求。

PR-07 未通过时，PR-08 和 PR-09 的生产接入保持阻塞；可以继续开发独立 fixture，但不能将原型宣布为最终聊天实现。触发 PR-X3 时保留相同样例和判定标准，比较完成后只保留一个生产渲染路线。WASM 宿主的可选 Sandbox 对照不改变阶段 B 的必需交付。
